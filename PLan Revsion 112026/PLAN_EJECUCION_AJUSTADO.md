## Condiciones de ejecución y compatibilidad

Las decisiones adicionales del PO del 04/11 para I07, I09, I10, I12, I13, I16 e I18a están registradas en [decisiones de incrementos](../documentacion/desarrollo/decisiones-po-20261104.md). I09 conserva costos/vigencias existentes, pero el costo no se usa operativamente por ahora. I13 admite ticket fiscal con CAE en Libro IVA aunque falle la impresión Hasar; otros gravámenes se difieren. I16 queda en efectivo con aprobación de otro administrador y permiso específico. I18a usa proveedor de catálogo con snapshot y recepción efectiva aprobada una sola vez.

1. **Base única:** `carnicerias_test_visual` en PostgreSQL Docker local `:55433`. No crear, clonar, provisionar ni reiniciar otra base de Carnicerías. La base `postgres` es solo mantenimiento del servidor. Las pruebas con escritura se limitan a fixtures identificados y limpiables en esta base; excluir la suite que crea/reinicia bases de test. El PO autorizó continuar con los puntos del plan, sin cambiar esta restricción.
2. **Migraciones futuras:** conservar todas las existentes y scripts. Antes de aplicar una migración: inventario de datos relevantes en la base única, respaldo verificable, revisión de compatibilidad con lectores/escritores viejos, orden de despliegue y plan de reversión. Preferir cambios aditivos. No convertir históricos por inferencia, borrar vigencias ni recalcular ventas/facturas. La reversión de código no debe perder pagos, piezas, cierres ni documentos nuevos.
3. **Pruebas:** base H0 observada: 96 tests .NET Architecture, 205 Angular, 97 Electron y 7 focalizados de cálculo/fiscalidad. No se repiten en este trabajo documental. En cada incremento aprobado: pruebas focalizadas y regresión proporcional del flujo afectado, build API/Web/Electron cuando corresponda; POS visual únicamente dentro de Electron. Admin puede probarse en navegador. Registros de prueba deben indicar entorno, resultado y límites.
4. **Seguridad y concurrencia:** toda API nueva verifica empresa/sucursal/terminal y permiso en servidor; guard de Angular no basta. Dinero/stock/piezas necesitan estado previo/final, idempotencia, transacción y recuperación. Reutilizar `RequireOperationalPermission`, ledger, snapshots y transacciones existentes. Las funciones de admin no duplican pantallas de Negocio/Configuración.
5. **Arquitectura:** Q1 y Q15 están resueltas funcionalmente: la apertura toma el último cierre de la misma caja física, con fondo nuevo independiente; los códigos de bulto convierten unidades solo en recepción. El diseño de entidades/servicios de I20 y el contrato de Producción de Q17 requieren revisión del PO antes de implementar esos incrementos. PEND-01/PEND-02 (balanzas en construcción) siguen excluidos. Producción se rige por `05_PRODUCCION_BACKOFFICE.md`, sin usar pasajes 137–167 de la transcripción.

## Primer incremento concreto para aprobación separada: I01 / MEJ-08

**Objetivo acotado:** filtrar las ventas del historial administrativo por el tipo de comprobante ya persistido (`ConfirmedSale.DocumentType`). Los valores existentes son `nonFiscalTicket`, `fiscalTicket` y `electronicInvoice` (`src/Carnicerias.Infrastructure/SaleDocumentChoice.cs:5,22-26`). El listado ya consulta empresa/sucursal/caja/fechas y pagina (`AdminHistoryEndpoints.ListSalesAsync:116-145`), y el detalle ya traduce esos tipos (`:160-164`). La UI existente `HistoryPage` administra filtros y paginación; se agregará allí un selector visible solo en la pestaña Ventas. No se crea pantalla, campo, endpoint paralelo, permiso ni migración.

**Archivos previstos:** `src/Carnicerias.Api/History/AdminHistoryEndpoints.cs` (parámetro opcional, validación de literal y filtro EF antes de contar/paginar); `src/Carnicerias.Web/src/app/core/admin/admin-history-client.ts` (parámetro de consulta solo para ventas); `src/Carnicerias.Web/src/app/features/admin/history-page.ts` y `.html` (estado, selector, página 1 al cambiar tipo); `src/Carnicerias.Web/src/app/features/admin/history-page.spec.ts` (filtros y tabs). `SaleDocumentChoice.cs` se lee, sin necesidad prevista de editarlo. Si la validación de API requiere test puro, se agregará una prueba focalizada al proyecto de tests existente, sin crear BD.

**Aceptación:**

1. Sin filtro, resultado idéntico al actual. Con cada uno de los tres tipos, `totalItems` y páginas reflejan **solo** ese tipo y respetan empresa, sucursal, caja y período. Un valor desconocido devuelve error de validación, no resultados silenciosamente incompletos.
2. El selector solo aparece en Ventas; al cambiarlo vuelve a página 1. Otros tabs nunca reciben `documentType` y siguen igual. El modal de detalle y permiso `organization.manage` conservan su comportamiento.
3. La consulta es de solo lectura: no modifica ventas, facturas, caja, stock, historial fiscal ni costo. No recalcula comprobantes históricos.

**Pruebas/evidencia propuestas una vez autorizado:** ampliar `history-page.spec.ts` con `HttpTestingController` para combinación de filtros, cambio de página/tab y valor sin filtro; validar build de API y tests puros existentes; consulta GET de solo lectura sobre la **única** base permitida para comprobar conteos y pertenencia, usando datos ya presentes. Si allí faltan ventas de algún tipo, registrar ese límite y no sembrar datos sin autorización. No ejecutar la suite de integración que crea/reinicia BD. Admin puede verificarse en navegador; no hay cambio visual en POS.

**Riesgo y reversión:** riesgo bajo, concentrado en la traducción literal→enum, el orden del predicado antes de `LongCountAsync` y la persistencia del selector durante paginación. Revertir conjuntamente el parámetro, cliente y selector si falla; como no hay esquema/datos nuevos, la respuesta sin parámetro sigue compatible. No se necesita backup de datos para este cambio de solo lectura, pero se conserva la política general antes de cualquier migración futura.
