# Mercado Pago: QR dinámico y Point (pruebas)

## Objetivo y alcance

El cajero puede iniciar un cobro presencial QR dinámico o Point para el ticket A–D activo y confirmar la venta **solo después** de que Mercado Pago informe orden `processed` y pago `processed/accredited` por el mismo importe y referencia. Otros proveedores tendrán configuración y adaptadores propios; `PaymentMethod.MercadoPago` no es una aprobación autodeclarada. Se permiten pagos mixtos; la parte Mercado Pago tiene una única orden por borrador activo.

## Configuración

`Configuración → Pasarelas de cobro` requiere `organization.manage`. Guarda User ID vendedor de prueba, Access Token y secreto de webhook por empresa; los secretos se protegen con ASP.NET Data Protection y la API solo devuelve indicadores de presencia. Cada caja local puede tener `external_pos_id` para QR y/o `terminal_id` Point. Los IDs deben pertenecer a la misma cuenta vendedora; por ahora se crean/vinculan en Mercado Pago, no automáticamente en esta pantalla. Los archivos locales `Documentos/MP/` están fuera de Git. Al trasladar la API a otro servidor se debe conservar el almacén de claves Data Protection además de PostgreSQL.

El webhook para ambos modos es `POST /api/payments/mercado-pago/webhook?data.id=...&type=order`. Mercado Pago exige una URL HTTPS pública, evento «Order (Mercado Pago)» y clave secreta. En el sandbox de una cuenta vendedora de prueba, su documentación indica configurar los webhooks en «Modo productivo» **de esa cuenta de prueba**; esto no convierte nuestra integración en producción. Si no hay URL pública, el cajero usa «Consultar pago» y el servidor consulta `/v1/orders/{id}`. [Point](https://www.mercadopago.com.ar/developers/es/docs/mp-point-v2/notifications?scope=prod), [QR](https://www.mercadopago.com.ar/developers/es/docs/qr-code/notifications?scope=prod).

## Flujo y seguridad

1. `POST /api/sales/drafts/{draftId}/mercado-pago` recibe `{mode: "qr"|"point", amount}`. Exige sesión, caja, turno abierto, borrador propio y configuración del modo. Persiste la intención y clave idempotente antes de llamar a `/v1/orders`. QR usa `config.qr.mode=dynamic` y `external_pos_id`; Point usa `config.point.terminal_id`. Nunca se envía información personal en `external_reference`. [Orders QR](https://www.mercadopago.com.ar/developers/es/docs/qr-code/payment-processing), [Orders Point](https://www.mercadopago.com.ar/developers/es/docs/mp-point-v2/payment-processing?scope=prod).
2. `GET` recupera el intento tras un reinicio; `POST /{intentId}/check` consulta a Mercado Pago. Si se perdió la respuesta de creación, la API busca la orden por `external_reference` persistida y recién entonces consulta su ID, tipo e importe. Incluso un HTTP 400 no prueba que no exista una orden: en el sandbox se observó una orden `created` tras esa respuesta. Respuestas pendientes y errores de red no son pago. El webhook valida `x-signature` y `x-request-id`, busca la orden y vuelve a consultar el estado por API. No usa el estado recibido en el cuerpo como autorización de cobro. [Búsqueda de órdenes](https://www.mercadopago.com.ar/developers/es/reference/online-payments/checkout-pro/search-orders/get).
3. `POST /{intentId}/cancel` solicita cancelar la orden pendiente; si el resultado es incierto, el ticket sigue protegido y se consulta. Una orden aprobada no se cancela por esta vía: el reembolso es un flujo distinto pendiente.
4. Al confirmar la venta, la API exige el ID de la intención acreditada, mismo borrador, turno, caja, cajero e importe. La venta, pago, egreso de stock y vínculo de intención se guardan en una transacción. Un borrador con orden activa no puede modificarse ni cerrarse en efectivo por detrás. El ticket continúa recuperable ante corte de luz.

## Estado del sandbox y pendientes

- El User ID y Access Token del archivo local de sandbox ya están cifrados en la única base de desarrollo. `GET /users/me` respondió 200 y el ID de la cuenta coincide; nunca se guardan el token ni el archivo en Git.
- Caja 1 de Sucursal Visual usa Point virtual `NEWLAND_N950__SBX0000001`. Se creó una order de prueba de $20 con estado `created`; **no se acreditó ningún pago**. El endpoint normal de cancelación devolvió 403 `forbidden_checking_device_owner` para la terminal virtual. La simulación oficial `POST /v1/orders/{id}/events` aceptó `canceled` (204) para esa order; otras solicitudes de prueba no pudieron cancelarse con el mismo endpoint (404) y deben dejarse expirar. No se simula una aprobación automáticamente desde el POS. [Pruebas Point](https://www.mercadopago.com.ar/developers/es/docs/mp-point/integration-test?scope=prod).
- Prueba de punta a punta en Electron (9/10/2026): Caja 1/cajero1, Ticket A, una gaseosa de $2.500. El POS creó la orden Point `ORDTST01M4HA805EMC4V0Q6AGGT8097W`; la simulación oficial de sandbox respondió 204, luego `/v1/orders/{id}` informó `processed/processed/accredited`. «Consultar pago» habilitó el cierre y se registró la venta ficticia `4cee09f9-5bfa-4ee6-a977-d1239202982a`. Una consulta de solo lectura a `carnicerias_test_visual` confirmó total $2.500, pago Mercado Pago $2.500 e intención aprobada vinculada a esa venta. Se descontó una unidad del stock ficticio. **No hubo cobro con dinero real.**
- El sandbox rechazó $1 para Point con un mínimo observado de $15. El POS/API ahora valida ese mínimo para Point, sujeto a revisar si Mercado Pago cambia su regla.
- QR de sandbox ya tiene sucursal Mercado Pago `81945453` (`CARNICERIASVISUAL01`) y caja activa `139240371` (`CARNICERIASVISUAL01CAJA1`, modo `pdv`). Se crearon por API con el Access Token de prueba y la ubicación que indicó el usuario, geocodificada mediante la [API Georef argentina](https://apis.datos.gob.ar/georef/api/); la dirección exacta no se replica en Git. El `external_pos_id` quedó vinculado a Caja 1 en Administración sin quitar su terminal Point. La API de Mercado Pago exige ubicación correcta y puede mostrar la sucursal en sus mapas; no reutilizar esta configuración de prueba en producción. [Crear tienda y caja QR](https://www.mercadopago.com.ar/developers/es/docs/qr-code/create-store-and-pos).
- Prueba QR en Electron (9/10/2026): Caja 1/cajero1 creó tres órdenes dinámicas de $2.500 para una gaseosa ficticia; el POS dibujó el QR y `Consultar pago` mantuvo la orden pendiente. Las órdenes se cancelaron desde el POS, que informó fin sin cobro; ninguna confirmó venta ni descontó stock. La interfaz muestra «Cancelado» y oculta el QR inválido después de cancelar. Falta la prueba de acreditación QR con una cuenta compradora de prueba y verificar la conciliación al cerrar la venta. [Prueba de compra QR](https://www.mercadopago.com.ar/developers/es/docs/qr-code/test-integration/test-purchase).
- Configurar URL HTTPS pública y clave de webhook; o probar inicialmente con consulta manual.
- Validar desde el POS con comprador de prueba el escaneo QR y, en Point, los estados rechazado, timeout, cancelación y reintento. La aprobación Point y el cierre de venta sí se verificaron de punta a punta; aún falta automatizar esa verificación sin crear otra base.
- Automatizar conciliación periódica de órdenes pendientes si no llega webhook, y diseñar reintegros asociados a venta/turno. Revisar el nombre heredado de `PointPaymentIntent` al extender a otros proveedores.

No ejecutar tests de integración que creen otra base. Las pruebas de transporte y dominio usan respuestas simuladas; la verificación PostgreSQL se limita a la única base `carnicerias_test_visual`.
