# I18b destino e I21 — implementación para demostración

Fecha: 06/11/2026. Rama: `feature/ui-v2`. Base única: `carnicerias_test_visual` en el contenedor existente `carnicerias-pos-test-20261007`, puerto local `55433`. No se creó, clonó ni reinició una base.

## Recepción de transferencias en destino (I18b)

- Administración → Negocio → **Recepción entre sucursales**. Se puede importar el JSON exportado por el origen o crear un remito manual con nombre de sucursal de origen, número y fecha. El ID interno de origen es opcional. El JSON no está firmado: el hash guardado identifica los datos declarados recibidos, no acredita autenticidad.
- El borrador separa cantidad enviada y recibida; la aprobación acredita únicamente la recibida, en transacción serializable, con movimiento `TransferIn` por renglón. Un faltante completo queda con diferencia pendiente y sin movimiento. Las diferencias se resuelven por administrador con motivo, sin alterar de nuevo el stock.
- Una pieza se lee físicamente con fórmula de código configurable. Si el despacho local es verificable, se valida su línea, pieza y estado `Transferred`; la tenencia nueva conserva `OriginPieceId`. Si el origen es externo, el identificador de origen queda declarado, no verificado. Un índice único de tenencia activa y otro de vínculo de origen evitan duplicaciones.
- El kardex existente incluye `transferIn`, cantidad y referencia al remito de destino. El despacho de origen sigue independiente y no requiere que el destino use el POS.

## Conteo físico y aprobación (I21)

- Administración → Negocio → **Conteo físico**. Un usuario con `inventory.stock.manage` crea el borrador, registra mediciones por artículo y lo envía a revisión. Solo una asignación de rol `administrator` de la misma empresa puede aprobar o rechazar con motivo.
- Cada renglón conserva saldo, reserva, stock protegido, cuarentena, último movimiento, usuario y fecha al contar. La aprobación serializable compara esos datos con el estado actual. Si cambió el saldo o el último movimiento, responde `COUNT_STALE_RECOUNT_REQUIRED`: se rechaza ese documento y se hace un nuevo conteo. Las cajas siguen operando durante todo el proceso.
- Para artículos con saldo teórico se genera `PhysicalCountAdjustment` solo por la diferencia. La operación usa el ID de línea como clave idempotente y evita reducir la cantidad protegida por piezas o reservas. Un segundo intento de aprobación no duplica el movimiento.
- La categoría define `TheoreticalStock` por defecto, preservando los artículos existentes. Un artículo por peso puede sobrescribirlo con `MassObservation`, que registra la masa observada y la referencia contable sin crear stock teórico anatómico ni movimiento. Los artículos por unidad siempre conservan saldo por artículo. La vista muestra suma de masa física y referencia contable de los renglones de peso del documento; **no calcula rendimientos teóricos ni un balance por período**.
- Para esta demo, la aprobación administrativa se aplica solo a las diferencias de este documento. Los ajustes manuales y Excel no cambian. Esta delimitación se revisará con el PO después de la presentación.

## Recorrido de demo

1. Iniciar la API POS en `5197` y el administrador Angular en `4200` con [los comandos locales](../despliegue/check-arranque-local.md). Entrar a Administración de La Rústica.
2. Abrir **Recepción entre sucursales**. Crear un remito manual o descargar el JSON de un remito despachado en **Transferencias** e importarlo. Registrar la cantidad física y aprobar. Consultar el movimiento `transferIn` en Historial → Stock.
3. Abrir **Conteo físico**. Crear borrador, agregar un artículo, enviar y aprobar con motivo como administrador. Ver el ajuste en Historial → Stock. Para demostrar la guarda de obsolescencia, registrar un segundo conteo y modificar el stock antes de aprobarlo; el sistema pedirá recuento.
4. En la misma pantalla, configurar una categoría o excepción de artículo de peso como **Solo medición de masa**. Registrar un conteo y comprobar que la medición queda documentada sin ajuste contable.

## Límites para revisar después de la demo

- El JSON de transferencia no certifica origen ni integridad criptográfica. La decisión humana de aprobar sigue siendo obligatoria.
- La pantalla de conteo resume masa observada del documento; el balance de masa por proceso o período y la configuración por proceso mencionada por el PO siguen pendientes de definición e implementación.
- La lectura física de una pieza transferida y el flujo completo entre dos Electron no se homologaron en esta ronda. La prueba HTTP cubre cantidades genéricas; los tests puros cubren las reglas de pieza.
