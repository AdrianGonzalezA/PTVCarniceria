# Administración central: migración controlada en laboratorio

La API central y la API POS son procesos separados. Durante este desarrollo comparten **únicamente** la base existente `carnicerias_test_visual` del PostgreSQL Docker, publicada en `127.0.0.1:55433`. Las tablas centrales usan el esquema `central_access` y su propio `__EFMigrationsHistory`. La API central **no migra al arrancar**. No crear otra base ni ejecutar la suite de integración que la provisione.

## Antes de migrar

1. Confirmar con `docker ps` que el contenedor esperado publica `127.0.0.1:55433->5432/tcp`. Confirmar con `psql` que `current_database()` es `carnicerias_test_visual` y existen `platform_access` y `pos_sales`.
2. Generar un nombre **nuevo** de respaldo `.dump` y ejecutar `docker exec <contenedor> pg_dump -U postgres -d carnicerias_test_visual -Fc -f /tmp/<nombre>.dump`. El archivo nunca debe sobreescribir un respaldo anterior.
3. Verificar `docker exec <contenedor> pg_restore --list /tmp/<nombre>.dump`: debe terminar con código cero e indicar `dbname: carnicerias_test_visual` y formato `CUSTOM`.
4. Copiar con `docker cp <contenedor>:/tmp/<nombre>.dump .local-backups/<nombre>.dump`. Comparar `docker exec <contenedor> sha256sum /tmp/<nombre>.dump` con `Get-FileHash -Algorithm SHA256 .local-backups/<nombre>.dump`. `.local-backups/` está excluido de Git y contiene el respaldo completo de datos ficticios; mantenerlo protegido.
5. Revisar el SQL idempotente con `dotnet ef migrations script --project src/Carnicerias.Central.Infrastructure --startup-project src/Carnicerias.Central.Api --context CentralAccessDbContext --idempotent`. Debe afectar exclusivamente `central_access`.

La cadena de conexión se proporciona **solo** mediante `CARNICERIAS_CENTRAL_CONNECTION_STRING` desde la configuración protegida de la máquina. No pasar la contraseña como argumento ni guardarla en Git o en el historial de comandos. El comando de laboratorio rechaza cualquier host, puerto o base distintos de `127.0.0.1:55433/carnicerias_test_visual`, y exige un respaldo reciente en formato custom cuyo SHA-256 coincida:

```powershell
dotnet run --project tools/Carnicerias.Central.Bootstrap/Carnicerias.Central.Bootstrap.csproj --configuration Release -- migrate --backup-file <ruta-absoluta-al-dump> --backup-sha256 <SHA256> --apply
```

La herramienta valida el destino antes de abrir la conexión, confirma la identidad de la base y la presencia de los esquemas POS, y aplica **solo** las migraciones de `CentralAccessDbContext`. Una ampliación a otro servidor o base requerirá una decisión y un guardia nuevos; no aflojar esta validación silenciosamente.

## Alta y recuperación inicial de cuentas centrales

Con la misma variable de entorno protegida y las migraciones centrales aplicadas, ejecutar desde una terminal **interactiva**:

```powershell
dotnet run --project tools/Carnicerias.Central.Bootstrap/Carnicerias.Central.Bootstrap.csproj --configuration Release -- manufacturer-create --username <superadmin-central>
dotnet run --project tools/Carnicerias.Central.Bootstrap/Carnicerias.Central.Bootstrap.csproj --configuration Release -- manufacturer-password-reset --username <superadmin-central>
dotnet run --project tools/Carnicerias.Central.Bootstrap/Carnicerias.Central.Bootstrap.csproj --configuration Release -- company-create --code <codigo-central> --name <nombre> --username <administrador>
dotnet run --project tools/Carnicerias.Central.Bootstrap/Carnicerias.Central.Bootstrap.csproj --configuration Release -- password-reset --code <codigo-central> --username <administrador>
```

La herramienta pide la contraseña dos veces sin eco y rechaza la entrada redirigida. El CLI actual verifica antes de conectar que su destino es exclusivamente `127.0.0.1:55433/carnicerias_test_visual`; **solo para esa base de laboratorio** admite seis caracteres. El generador central predeterminado mantiene un mínimo de 12 caracteres para cualquier otro uso. El formulario y el endpoint de *ingreso* aceptan una contraseña no vacía para poder verificar cuentas existentes, sin alterar la política de alta. No pasar claves como argumento, variable de entorno ni archivo. El reseteo invalida las sesiones existentes y registra el evento en la misma operación. Son cuentas distintas de las cuentas de cada sucursal. No hay contraseña predeterminada.

`manufacturer-create` es el **bootstrap único** del SuperAdmin del portal central. Si ya existe uno, el comando rechaza crear otro. Después de aplicar la migración `AddCentralManufacturerAccess`, ese usuario entra en `/superadmin` del sitio central. Allí crea empresas centrales con su primer administrador y agrega otros administradores por empresa. La creación de empresa, administrador inicial y auditoría es atómica; el código de empresa es único. Este SuperAdmin **siempre pertenece a Recursos Informáticos**: no opera como administrador de ninguna empresa. `company-create` permanece como herramienta de implementación para recuperación o entornos de laboratorio, pero el flujo ordinario de alta pasa por el portal. El administrador de una empresa sigue entrando en `/` con su código de empresa; ni su sesión ni un SuperAdmin del POS autorizan `/superadmin`.

La migración y la creación real de esa primera cuenta deben verificarse sobre **la misma base existente** antes de ofrecer el acceso al equipo. No introducir una contraseña predeterminada ni copiar credenciales a Git. `manufacturer-password-reset` pide la nueva contraseña sin eco, audita el cambio y revoca todas las sesiones previas de esa cuenta; usarlo para recuperación operativa desde una terminal protegida.

## Registro protegido de una sucursal

Este procedimiento CLI corresponde a las instalaciones **heredadas** y a recuperación. El flujo ordinario nuevo del administrador central está en la sección siguiente. Antes de usar el CLI, implementación configura en el entorno protegido del proceso:

- `CARNICERIAS_CENTRAL_CONNECTION_STRING`: la misma base de desarrollo admitida por el guardia actual.
- `CARNICERIAS_CENTRAL_APPROVED_BRANCHES`: JSON de destinos exactos y **todas** las IP que puede devolver DNS, por ejemplo `[ { "url": "https://sucursal.interna:8443/", "addresses": ["10.10.1.25"] } ]`. El destino del comando debe coincidir; la central fija la IP validada al conectar y mantiene la validación TLS del nombre.
- `CARNICERIAS_CENTRAL_BRANCH_SECRET_<REFERENCIA>`: token de servicio de 32 bytes en hexadecimal (64 caracteres). La referencia se normaliza a mayúsculas y solo ella se graba en `central_access.installations`. Guardar el valor mediante el administrador de secretos/configuración protegida del servidor, fuera de Git y sin pasarlo como argumento. La API de sucursal almacena solo el SHA-256 de los **bytes** del token en `Federation:CredentialSha256`.

```powershell
dotnet run --project tools/Carnicerias.Central.Bootstrap/Carnicerias.Central.Bootstrap.csproj --configuration Release -- installation-register --company-code <codigo-central> --installation-id <uuid-estable> --remote-company-id <uuid-empresa-sucursal> --remote-branch-id <uuid-sucursal> --label <etiqueta> --url <url-aprobada> --secret-ref <REFERENCIA>
```

La sucursal debe responder `GET /api/central/v1/installation` con la credencial y los tres UUID exactos. Un duplicado, destino/credencial ausente, error TLS, redirección o discrepancia no crea instalación; se audita el rechazo sin token. El listado web informa *registrada*, no *conectada*. Para HTTP de laboratorio se requiere **además** `--allow-loopback-http`, URL literal `http://127.0.0.1:<puerto>/` y aprobación de `127.0.0.1`. No usarlo para la red real. `AllowedHosts` de la API de sucursal debe incluir exactamente el host aprobado; una variable de entorno heredada puede prevalecer sobre `appsettings.json` y producir `400 Invalid Hostname` aunque el puerto esté abierto.

El sitio Angular central y `/api/v1/*` deben publicarse bajo **el mismo origen HTTPS** mediante un proxy reverso. La cookie es `Secure`; un cliente HTTP de PowerShell no la reenvía automáticamente en el laboratorio. Para acceder por el proxy de desarrollo `localhost:4300`, la API central local debe admitir tanto `localhost` como `127.0.0.1` en `AllowedHosts`; con solo `127.0.0.1`, el proxy devuelve `400 Invalid Hostname`. Ese proxy solo sirve para probar la API, no sustituye la revisión de un navegador ni una publicación HTTPS. La API central no ejecuta migraciones al arrancar.

## Conexiones desde el administrador de cada empresa central

Con las migraciones `AddCentralBranchCredentials`, `AddCentralConnectionManagement` y `EnforceUniqueActiveRemoteBranch` aplicadas al **mismo** `carnicerias_test_visual`, el administrador de empresa entra al portal central y abre **Conexiones a sucursales**. La empresa propietaria sale de su cookie; no hay selector de empresa. El índice único impide que una misma pareja empresa/sucursal remota esté activa en dos empresas centrales, además del control de conflicto del servicio. Ni el SuperAdmin central de Recursos Informáticos ni el SuperAdmin local del POS usan esa pantalla con sus propias sesiones.

Para una sucursal en **modo administrado**, el administrador local obtiene los seis campos de la conexión en **Configuración → Conexión con central**, guarda antes su URL alcanzable y entrega el paquete de una sola exhibición al administrador de esta empresa central. El portal central permite **Pegar datos de sucursal** tanto al agregar como al editar una conexión de la misma identidad. No copiar identificadores ni tokens desde SQL, scripts o archivos. El proceso central sigue necesitando **antes del alta** la allowlist exacta de URL/IP para esa empresa y la clave protegida indicada en los puntos 2 y 3 siguientes. El paquete por sí solo no amplía la allowlist. La migración local y el vínculo fijo de la API están en [integracion-central-sucursal.md](integracion-central-sucursal.md).

Para una conexión **heredada**, implementación debe preparar además el punto 1:

1. En la sucursal: `Federation:Enabled`, `InstallationId`, `CompanyId`, `BranchId` y `CredentialSha256` según [integracion-central-sucursal.md](integracion-central-sucursal.md). Generar un token aleatorio de 32 bytes/64 hex; guardar en la sucursal **solo** SHA-256 de sus bytes. La sucursal debe responder `GET /api/central/v1/installation` con identidad exacta. Para rotar sin corte, preparar `NextCredentialSha256` antes de editar la central.
2. En la configuración protegida del **proceso API central**: `CARNICERIAS_CENTRAL_APPROVED_BRANCHES` con URL raíz exacta, todas las IP permitidas y `centralCompanyId` de esa empresa. Ejemplo sin valores reales: `[ { "url": "https://sucursal.interna:8443/", "addresses": ["10.10.1.25"], "centralCompanyId": "<uuid-empresa-central>" } ]`. Una entrada heredada sin `centralCompanyId` **no** autoriza altas web. DNS debe resolver únicamente a las IP aprobadas; el servidor fija la IP y verifica TLS del nombre. HTTP `127.0.0.1` requiere `CARNICERIAS_CENTRAL_ALLOW_LOOPBACK_HTTP=true` y aprobación exacta, **solo laboratorio**.
3. En la configuración protegida del mismo proceso: `CARNICERIAS_CENTRAL_CREDENTIAL_ACTIVE_KEY_VERSION=1` y `CARNICERIAS_CENTRAL_CREDENTIAL_KEY_V1=<64 hex aleatorios>`. La clave de 32 bytes se genera y respalda por un canal de secretos del servidor, **fuera de Git, de la base y del navegador**. No ponerla en la URL, comando, `appsettings` versionado ni plantilla de caja. Para rotarla: aprovisionar la nueva `KEY_V2`, mantener `KEY_V1` para descifrar filas antiguas, cambiar la versión activa y re-cifrar cada registro antes de retirar `KEY_V1`; la re-encriptación masiva aún no está automatizada. Si se pierde una clave, reprovisionar los tokens afectados desde las sucursales.

El administrador ingresa etiqueta, URL raíz, tres UUID y token. **Verificar y agregar** valida destino, token e identidad antes de guardar; el navegador limpia el token y nunca lo vuelve a mostrar. El listado muestra activas e inactivas, credencial disponible y resultado/fecha de la última comprobación, que **no es conectividad continua**. **Comprobar** hace una prueba puntual. **Editar** cambia la etiqueta sin consultar red; si cambia URL o token, verifica antes de reemplazar la configuración. **Desactivar** excluye la sucursal del dashboard sin borrarla; **Reactivar** exige comprobarla de nuevo. Si una acción vence por timeout, releer el listado antes de repetirla: una respuesta perdida no significa que no se guardó. Las conexiones heredadas del CLI siguen leyendo variables `CARNICERIAS_CENTRAL_BRANCH_SECRET_<REFERENCIA>`; para cambiarles el token por web hay que introducir uno nuevo y desde entonces usan la tabla cifrada. No hay fallback a esa variable si una credencial cifrada falla.

La lista aprobada es una política de Recursos Informáticos/implementación, **no** una opción editable por el administrador. Si la central muestra `BRANCH_CREDENTIAL_UNAVAILABLE`, comprobar la clave externa/versiones; ante `BRANCH_CONNECTION_UNVERIFIED`, comprobar aprobación URL/IP, TLS, sucursal en línea, token y tres UUID, sin pegar el token en logs o soporte. Los cambios quedan en auditoría con actor, empresa, instalación y resultado, nunca el secreto. El portal y `/api/v1/*` deben compartir origen HTTPS; el POS local no depende de la central.

## Consulta de negocio en vivo

La misma configuración protegida de destinos y credenciales usada para registrar una instalación debe estar disponible **también para el proceso de la API central** al consultar `/api/v1/business/summary`. Si falta, la instalación se informa no disponible; el registro por sí solo no comprueba conectividad. Solo para laboratorio local, `CARNICERIAS_CENTRAL_ALLOW_LOOPBACK_HTTP=true` habilita HTTP literal `127.0.0.1` ya incluido en los destinos aprobados. No habilitarlo en un despliegue por VPN: allí se usa HTTPS con nombre y certificado válidos.

La central obtiene las instalaciones activas de la empresa de la cookie, aprueba de nuevo el destino y lee `/api/central/v1/summary` sin enviar la cookie al POS. `GET /api/v1/business/summary` consulta el día corriente de Buenos Aires desde las 00:00 hasta el instante actual. Para un período distinto, pasar juntos `fromDate` y `toDate` (`yyyy-MM-dd`, fechas locales inclusivas) o juntos `fromUtc` y `toUtc` (instantes UTC). El máximo son 31 días. La respuesta no contiene URLs, referencias de secreto ni datos de tickets; el saldo de turnos abiertos se informa **por sucursal**, como fotografía separada de ventas. Una sucursal no disponible anula el agregado general, no los resultados individuales. Si dos instalaciones activas apuntan a la misma empresa/sucursal remota, ambas se marcan no disponibles para evitar doble conteo; el equipo de implementación debe corregir el registro. La fase remota tiene plazo global de 10 segundos, 4 conexiones simultáneas y 30 consultas/minuto por IP (`429` al excederlo).

El navegador sirve la pantalla desde el mismo origen que la API central; no abrir la ruta API como si fuera una página. No se requiere otra base ni se copian métricas de negocio a `central_access`. El sitio central puede revisarse en navegador; el POS sigue revisándose **solo en Electron**.
